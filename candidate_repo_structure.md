# Candidate Repository Structure

This document proposes a directory layout and branching strategy for `ef_ws` — a workspace that makes programming Unitree robots (G1, GO2) easier, especially for beginners.

---

## 1. Directory Layout

### Guiding principles

- A beginner should know exactly where to start without reading internal code.
- "Things you run" (examples, notebooks) are separated from "things that make it work" (sdk).
- Documentation lives in one place at the root.
- Build artifacts are never committed.
- Dead code is clearly labelled, not mixed with active code.

### Files and directories to remove or ignore

| Item | Action | Reason |
|---|---|---|
| `install/` | Add to `.gitignore` | Colcon build artifact, regenerated by `colcon build` |
| `log/` | Add to `.gitignore` | Colcon build logs, not source |
| `src/install/`, `src/log/` | Add to `.gitignore` | Same reason |
| `g1/hand_pose_navigation_copy/` | Delete | Working copy that leaked into the repo |
| Root `dev/` | Merge into `g1/tools/` | Redundant with `g1/dev/`, confusing at root level |
| `g1/scripts/dev/other/` | Flatten or archive | Three levels of `dev` nesting is disorienting |

## 2. Branch Strategy

### Overview

```
prod ──────────────────────────────────────────────────────► (public, stable)
  ▲                                                      
  │ merge when stable + documented                       
  │                                                      
main ──────────────────────────────────────────────────────► (integration)
  ▲             ▲              ▲              ▲           
  │             │              │              │           
feature/*    robot/g1       robot/go2      sim/*         
```

### Branch definitions

#### `prod` — public, stable, read-only for contributors
- **Audience:** beginners, external users, anyone cloning for the first time.
- **Content:** only code that is tested, documented, and works out of the box.
- **Rules:**
  - Never commit directly to `prod`.
  - Merges from `main` only, via pull request with at least one review.
  - Every merge to `prod` must have an updated `docs/` entry and a passing example script.
  - Tagged with semantic versions: `v1.0`, `v1.1`, etc.
- **What a beginner gets when they clone this branch:**
  - A clean directory tree (no `archive/`, no `tools/` clutter unless opted in).
  - Working `examples/` scripts they can run immediately.
  - Complete `docs/` with setup guide.

#### `main` — active development, integration branch
- **Audience:** contributors and the repo owner.
- **Content:** features that are complete but may not yet be fully documented or polished.
- **Rules:**
  - Feature branches merge here first.
  - CI runs here (linting, basic import checks).
  - Broken state is acceptable temporarily; `prod` is the stability guarantee.

#### `feature/<name>` — individual work-in-progress
- Short-lived. One feature or fix per branch.
- Naming examples: `feature/wbc-arm-control`, `feature/go2-slam-webapp`, `fix/fsm-switch-error`.
- Merges into `main` via pull request.

#### `robot/g1` and `robot/go2` — robot-specific staging (optional)
- Useful if G1 and GO2 development move at different paces.
- Acts as a secondary integration layer before `main`.
- Skip these if the team is small — they add overhead without benefit.

#### `sim/<simulator>` — simulation-only work (optional)
- For long-running simulation experiments that aren't ready for the main tree.
- Examples: `sim/mujoco-gait-tuning`, `sim/pybullet-wbc`.

### Branch protection rules (recommended)

| Branch | Direct push | Requires PR | Requires review | Status checks |
|---|---|---|---|---|
| `prod` | Blocked | Yes | Yes (1+) | Yes |
| `main` | Blocked | Yes | No | Yes |
| `feature/*` | Allowed | — | — | No |
| `sim/*` | Allowed | — | — | No |

### Merge flow

```
feature/my-feature
    │
    └──► main          (PR: code complete, basic test)
              │
              └──► prod     (PR: documented, example script works, version tag)
```

### What lives only on `prod`

To keep `prod` clean for public consumption, consider using a `.prodignore` approach or a CI step that strips these before merging:

- `archive/` — not useful to a beginner
- `tools/` — developer utilities, not beginner-facing
- `setup/` internal scripts that require internal credentials
- Any `*.log`, `*.csv` data files that aren't part of an example

Alternatively, maintain a separate `prod`-specific `.gitignore` or use a CI job that builds the `prod` branch from `main` by copying only the intended subset.

## 3. Release tagging convention

```
v<major>.<minor>.<patch>-<robot>

Examples:
  v1.0.0          ← first stable release (both robots)
  v1.1.0-g1       ← G1-only feature addition
  v1.1.1-go2      ← GO2 patch
  v2.0.0          ← breaking API change
```

Tags are applied only on `prod`.
