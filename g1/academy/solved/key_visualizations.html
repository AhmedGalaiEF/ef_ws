ComputeFrom raw DDS bytes to plottable xy

decode_xyz(msg, stride, max_points, z_min=-1.0, z_max=2.4):
    # reinterpret the PointCloud2 byte blob using the message's own field
    # offsets/point_step as a structured numpy dtype — no per-point Python loop
    raw = np.frombuffer(msg.data, dtype=struct_dtype)
    pts = stack(x, y, z)[::stride]                 # subsample
    pts = pts[isfinite(pts) & z_min <= z <= z_max]  # drop NaNs, keep a floor-to-head band
    pts = pts[evenly-spaced indices up to max_points]

transform_xy(pts, pose):                            # world/map-frame view only
    out.x = cos(yaw)·x − sin(yaw)·y + pose.x         # 2-D rigid transform using the
    out.y = sin(yaw)·x + cos(yaw)·y + pose.y         # live SLAM pose's yaw/x/y

SLAM-service topics already publish in map frame and skip the transform; raw sensor clouds (deskewed/Livox/collision/…) go through it only when the "World/map frame" radio is selected — switch to "Sensor frame" to sanity-check the live sweep against the accumulated map without the transform in the way.

2 · joint_control_dashboard.py — live 3‑D joint skeleton academy/visualizations/joint_control_dashboard.py  (Dash app, default http://<host>:8060)

No camera involved at all — this view is pure forward kinematics from the robot's sensed joint angles, redrawn as a 3‑D skeleton on every plot-interval tick.

Data & computeFrom 29 sensed joint angles to 30 world-frame points

compute_skeleton(q_values):        # q_values = 29 sensed joint angles (rad), from RobotLink.snapshot()
    for each joint id 0..28, in parent order:
        world_R = parent_R @ quat(joint)  @ axis_rotation(joint.axis, q)   # Rodrigues formula
        world_t = parent_t + parent_R @ joint.pos
    → {"pelvis": xyz, 0: xyz, 1: xyz, … 28: xyz}

Per-joint offsets/quaternions/rotation-axes/limits are constants embedded in the script, transcribed from the G1 29‑DOF MJCF (g1_29dof.xml) in the same 0–28 order sdk_wrapper.py's LOWCMD_JOINTS uses (legs 0–11, waist 12–14, arms 15–28). RobotLink polls the real sensed state in the background — this is a live digital twin of where the joints actually are, not of what was last commanded.

Plotbuild_skeleton_figure()

  • One go.Scatter3d "lines" trace per joint group (left_leg / right_leg / waist / left_arm / right_arm), each a None-separated chain of parent→child bone segments, colored per-group from the dashboard's fixed categorical palette.
  • One go.Scatter3d "markers" trace per group at each joint's world position; hovering shows "{joint name} (id {n})<br>{angle}°".
  • A diamond marker at the pelvis root.
  • Fixed data-aspect 3‑D scene; camera position is preserved across refreshes via uirevision="skeleton" — the same trick the SLAM map uses to keep pan/zoom stable, applied here to orbit/zoom instead.

Highlight / calculateTwo ways to move a joint

Per-joint control
  • Clicking a joint's marker (customdata = joint id) opens a modal: sliders for q, dq, kp, kd, tau and a ramp duration, bounded by that joint's own limits.
  • Normal mode — rt/arm_sdk, waist+arms only (legs stay on ai_sport). First edit ramps the arm_sdk weight 0→1 with the same smoothstep engage_arms() uses.
  • Dev mode — rt/lowcmd, all 29 joints, ai_sport stopped. Turning it on seeds every joint's hold target from its current sensed pose so nothing jumps when ai_sport lets go.
  • A live per-joint angle readout next to each control row, updated every tick from the same sensed_q driving the skeleton.
IK end-effector controller
  • A separate modal: 6 sliders — x/y/z (±0.35 m around the current position), roll/pitch/yaw (±π) — set an absolute target hand pose in base_link frame.
  • On Apply: ArmFK gets the current hand pose, ArmIK's damped-least-squares solver (max 24 iters, 5 mm / 0.02 rad tolerances — the same defaults sdk_wrapper.G1._arm_ik_solver() uses) solves the 7-joint arm solution.
  • The solution is written into the same per-joint command table as manual edits and ramped together as one coordinated 0.8 s move — only that arm's 7 joints change.
  • Identical ArmFK/ArmIK pipeline to recognition_app_v3.py's grasp planner — here driven by sliders instead of a detected object pose.

3 · recognition_app_v3.py — G1 Recognition Layer academy/visualizations/recognition_app_v3.py  (Dash app, served at http://<host>:8060)

A Dash/dash_bootstrap_components single-page app with two background threads feeding a shared, lock-protected STATE object, and a dcc.Interval that repaints the UI every 500 ms.

PipelineHow the data gets there before anything is drawn

  1. Camera loop (_camera_loop, its own thread at --camera-rate-hz): pulls one RGB-D frame from a ZMQ SUB socket (_ZmqRgbdRobot.get_rgbd), draining the queue so the UI always works from the newest frame. A frame is 2–3 multipart messages: JPEG RGB, PNG depth (decoded, converted to grayscale if needed), and an optional 4-byte float depth_scale (default 0.001 m/unit) — multiplied in to get depth_m. Stores rgb_bgr, depth_m, and last_frame_ts on STATE.
  2. Perception loop (_perception_loop, its own thread at --rate-hz, independent/slower than the camera loop): on each new frame, runs the open-vocabulary NL-prompted VisionDetector to get 2‑D boxes, then per box:
    • mask_from_box_depth — keeps only pixels inside the box whose depth is within 0.05 m of the box's own median depth (cuts the object out from the table/wall behind it);
    • pose_from_mask — back-projects the masked pixels to a camera-frame 3‑D point cloud and fits an oriented pose via PCA/SVD (position = centroid; orientation from the largest/smallest-variance axes, "up" flipped to face the camera);
    • estimate_grasp_surface — reuses that PCA to get the object's in-view width_m/length_m footprint and how far its near surface sits in front of the centroid, for sizing the grasp standoff.
    Detections are held for DETECTION_HOLD_S=1.5 s past their last sighting (so one slow vision call or a motion-blur frame doesn't blank the overlay) and only pruned after that.
  3. Staleness: if no fresh camera frame or detection has landed in STALE_AFTER_S=4 s, the refresh callback clears the detection list/overlay and shows a STALE/DETECTING banner instead of serving frozen data as if it were live.

Grasp-surface mathWhat estimate_grasp_surface actually computes

points = back-project(masked pixels, depth)         # camera-frame XYZ point cloud
centroid = mean(points)
e0, e1, e2 = PCA axes of (points − centroid), most→least variance   # via SVD
e2 flipped to face the camera (dot(e2, centroid) > 0 ⇒ negate)

length_m  = max(proj·e0) − min(proj·e0)             # long in-view axis
width_m   = max(proj·e1) − min(proj·e1)              # short axis a pinch grasp closes across
near_surface_offset_m = max(proj·e2)                 # closest point ahead of the centroid
confidence = min(1, point_count / 400)

Coarse by design — a top-down/side-pinch approximation from one depth frame's PCA, not a 6-DoF pose network. It's what sizes the grasp standoff (_grasp_standoff_for_surface) and — via the object mass field — the target fingertip pressure and lift stiffness.

4 · dex3_input_viz.py — Dex3 tactile input academy/visualizations/dex3_input_viz.py  (Dash app, default http://<host>:8071)

A read-only monitor: no publish loop, no arm/hand control — it only polls sdk_wrapper.G1.get_dex3_hand_sensors(hand="both") (i.e. rt/dex3/{left,right}/state's press_sensor_state) at 8 Hz and compares every reading against one configurable contact threshold, live.

DataPads, taxels, and the invalid-reading sentinel

Each hand's snapshot has an unlabeled list of pressure pads — the DDS message itself doesn't name them, so neither does this script (shown as "pad 0", "pad 1", …) — each holding an array of raw per-taxel readings. A taxel reading equal to TACTILE_INVALID_VALUE=30000.0 means "sensor dropout this tick", not "zero pressure", and is excluded from every max/plot rather than plotted as a real low reading — the same convention recognition_app_v3.py's tactile readout (_is_invalid_tactile_value) and test_dex3_tactile.py use for this identical field.

5 · zmp_viz.py — ZMP / support polygon academy/visualizations/zmp_viz.py  (Dash app, default http://<host>:8072)

No force or pressure foot sensors are read here — the SDK doesn't expose any — so both halves of this view are estimates from geometry and odometry/IMU, in the same openly-approximate spirit as segmentation.py's PCA grasp-surface estimate: good enough to see whether the robot looks balanced, not a certified stability computation.

ComputeSupport polygon — leg forward kinematics + convex hull

leg_q = get_lowstate()["joint_positions"][0:12]      # 12 sensed leg joint angles
frames = foot_frames(leg_q)                           # same FK composition as joint_control_dashboard.py,
                                                        # scoped to just the leg chain (duplicated, not
                                                        # imported — that file has page-load side effects)
left_corners  = 4 corners of a fixed foot rectangle at frames[5]   (left ankle-roll)
right_corners = 4 corners of a fixed foot rectangle at frames[11]  (right ankle-roll)
support_polygon = convex_hull(left_corners ∪ right_corners)   # hand-rolled monotone chain, no scipy

The foot rectangle's half-length/half-width are UI-configurable (defaults 0.10 m / 0.045 m) — the SDK doesn't hand over the real foot outline either, so this is an adjustable placeholder, openly labeled as one, not a spec. The polygon is always drawn as double support: there's no foot contact/force sensing available to detect a single-support phase.

ComputeZMP — the LIPM / cart-table approximation

ZMP_xy = CoM_xy − (h_com / g) · CoM_accel_xy
TermWhere it comes from
CoM_xyApproximated by the pelvis/base position from get_odom() (no per-link mass data is available to compute a true whole-body CoM).
h_comA configurable assumed CoM height, default 0.793 m — the same fixed pelvis height joint_control_dashboard.py's PELVIS_POS uses.
CoM_accel_xyget_imus()["acc"] (body-frame accelerometer), rotated into world frame via the IMU roll/pitch/yaw and gravity-compensated (a_world = R·a_body − [0,0,g]), then smoothed over the last 5 samples — raw accelerometer noise would otherwise dominate the estimate.

Plot / highlightThe 2‑D view

  • Support polygon: filled translucent region (the convex hull), with each individual foot rectangle also outlined (dotted) so the hull's construction stays visible, not just its result.
  • CoM marker (orange circle) and ZMP marker (diamond) plotted separately, so their divergence — the whole point of the dynamic correction term — is visible rather than collapsed into one dot.
  • ZMP marker colored green when it's inside the support polygon (point-in-polygon via ray casting), red when outside; a status line reports the signed margin in cm (distance to the nearest polygon edge, negative when outside) via the same edge-projection math used for the color.
  • A short trailing line (last 5 s) of the ZMP's own path, useful for seeing it move during walking rather than only at a single instant.

7 · Reusable techniques cheat-sheet

  • Big point clouds → Scattergl, not Scatter: the SLAM map's 11 layers plus occupancy/KISS-ICP overlays all use WebGL-backed traces — the point counts (up to tens of thousands per layer) would stall a plain SVG scatter.
  • Keep pan/zoom stable across auto-refresh: give the figure a fixed uirevision string; both the SLAM map (2‑D pan/zoom) and the joint skeleton (3‑D camera orbit) rely on this so a 500 ms–2 s redraw doesn't reset the view.
  • Click-anywhere-to-target: the SLAM map's invisible background scatter grid is a cheap way to let clickData report a coordinate even where nothing is actually drawn.
  • Forward kinematics for a live skeleton: walk the joint tree in parent order, world_R = parent_R · quat(joint) · axis_rotation(joint.axis, q) (Rodrigues formula for the axis term), world_t = parent_t + parent_R · joint.pos — 29 joints, no physics engine needed, just the MJCF-sourced offsets/axes and the sensed angles.
  • Stream frames into a plain <img>/html.Img: encode each frame to JPEG bytes, base64, prefix data:image/jpeg;base64,. No canvas/WebGL/video element needed — a polling interval (500 ms here) is enough for a monitoring UI.
  • Depth → heatmap: clip to a sane max range, scale to 0–255, applyColorMap(..., COLORMAP_JET).
  • Mask overlay: alpha-blend a flat color into the RGB array only where the boolean mask is true — cheap, no extra drawing library.
  • 3‑D pose on a 2‑D image: pinhole-project with the known intrinsics (fx, fy, cx, cy) and cv2.drawFrameAxes/cv2.projectPoints; chain camera↔base transforms as 4×4 homogeneous matrices.
  • Cheap 6-DoF-ish pose/size from depth: back-project a masked region to a point cloud, PCA/SVD for orientation and extents — good enough for a standoff or grip-force scale, not for tight tolerances.
  • Anti-flicker for async detections: hold last-seen results for a short window before dropping them (DETECTION_HOLD_S), but still expire them if the source truly goes stale (STALE_AFTER_S) — don't let a UI show confident data from a dead feed.
  • A relocated script's sys.path hack is a landmine: anything computed as Path(__file__).parent.parent (or similar) silently points somewhere else once the file moves to a different depth — either fix the math or make the script resolve its local deps from its own directory instead.
  • A hand-rolled convex hull is enough for a support polygon: Andrew's monotone chain over ≤8 points needs no geometry library; pair it with a plain ray-casting point-in-polygon test and you get an in/out check and (via nearest-edge distance) a margin, for free.
  • The LIPM/cart-table ZMP formula turns odometry+IMU into a stability estimate: ZMP = CoM_xy − (h/g)·CoM_accel_xy, with CoM approximated by the base position and h a fixed assumed height — coarse, but real-time-computable from data every dashboard here already has, no per-link mass model required.
  • A shared "age badge" beats a bare timestamp: fresh/aging/stale bucketed off one poll timestamp, reused across every panel in state_monitor.py — cheaper than per-field staleness and still enough to stop a frozen feed from reading as confidently live.
