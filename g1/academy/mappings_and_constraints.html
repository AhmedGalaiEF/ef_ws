1. FSM states (LocoClient.SetFsmId)

The G1 locomotion controller is a finite-state machine selected by an integer FSM id. Academy code only exercises a safe subset; the wider repo shows a few additional ids seen on real firmware/dashboards. get_state() in sdk_wrapper.py reads the current id/mode via the raw RPC ids ROBOT_API_ID_LOCO_GET_FSM_ID / ROBOT_API_ID_LOCO_GET_FSM_MODE (numeric values are internal to unitree_sdk2py.g1.loco.g1_loco_api and not re-declared anywhere in this repo).

Motion-switcher modes (separate from the loco FSM)

MotionSwitcherClient is a second, independent state machine that arbitrates which high-level service owns the robot's motors. ai_sport is the normal locomotion-service mode; when a non-ai_sport name is selected (or the mode is released), the loco FSM RPCs described above stop being meaningful and the robot is in "dev" mode — get_state()/mode_control.py both check this first and skip the FSM RPC while motion_mode != "ai_sport".

get_slam_info() output — rt/slam_info / rt/slam_key_info

Both are std_msgs/msg/String carrying a JSON payload; get_slam_info() returns the raw string, and _parse_slam_pose() extracts a pose from it. get_slam_key_info() and get_slam_notice() (new) expose rt/slam_key_info directly plus the parsed errorCode/info/is_arrived/obsInfo envelope via _parse_slam_status()/_slam_notice(), timestamped so callers waiting on arrival can tell a fresh notice from a stale one. Previously this field was parsed nowhere and every wrapper polled current_pose() distance only. WRAPPER
data.obsInfo.stateThe actual obstacle-blocked flag — true while the nav stack currently has the path blocked (e.g. a person standing in it). Shape confirmed by a live rt/slam_info capture: "obsInfo": {"state": false, "time": 0.0} (see dev/slam_viz_in_jupyter.ipynb). keyDemo.cpp itself never reads this field by name — it just prints whatever info string comes with a non-zero top-level errorCode, so on the stock demo an obstacle stop only ever shows up as generic yellow text, not a labeled "obstacle" message. The wrappers now parse obsInfo.state directly instead (_parse_slam_status() / _parse_status() / parse_status(), depending on the file) so the UI/console can label it explicitly.
data.progress, data.stateMachinePresent in a live sample (an object with completion_percentage/last_time/used_time, and one with state/isPause/isBack/isRotate/isClimbStairs/isOpenPlan/ctrName/vx/vy/vyaw, respectively); the wrappers' new status parsers surface completion_pct and nav_state/nav_paused from these but don't otherwise act on them.

A message whose parsed pose is exactly (0, 0, 0) (position and yaw all below 1e-5) is treated as "no pose yet" and discarded by _parse_slam_pose() — the wrapper keeps returning the last known good pose (_last_slam_pose) instead.

Message type values seen in practice: "pos_info" (bare pose, what keyDemo.cpp's slamInfoHandler reads from rt/slam_info), "ctrl_info" (the fuller status blob above, streamed continuously while navigating — see the live sample in dev/slam_viz_in_jupyter.ipynb), and "task_result" (a terminal per-target result on rt/slam_key_info, what keyDemo.cpp's slamKeyInfoHandler waits on). The status parsers added to every wrapper handle all three without gating on type — they just read whichever of these fields happen to be present.
