# G1 Academy: Crucial Developer Skills

## 1. Core DDS and communication helpers

- Set up and validate the DDS environment reliably.
- Provide a global channel-initializer guard so DDS channels are initialized once, predictably, and before helpers use them.
- Build reusable topic/client subscriber and publisher helpers.
- Understand topic types, client/service calls, publisher lifecycles, and how to diagnose unavailable or stale signals.

## 2. Robot-state reading helpers

Create a consistent, dictionary-based interface for robot state, including:

- `get_lowstate()` — joint poses and velocities, IMU/state fields, battery information, and other relevant low-level state.
- `get_odommodestate()`
- `get_battery()`
- `get_slam_info()`
- `get_occupancygrid()`
- `get_rgbd()`
- `get_services()`

The aim is to make higher-level tasks independent of raw DDS message layouts.

## 3. Mode-switching helpers

- Implement `damp_mode` safely.
- Implement `toggle_service` and `toggle_gait`.
- Implement reusable helpers such as `set_headlight(color)` and `say(language, text)`.
- Implement `toggle_custom_mode(mode_name, language, voice, headlight_color)`.
  - Announce the selected mode using Piper text-to-speech in the requested language and voice.
  - Run a thread that continuously displays the selected headlight colour until the mode is exited.
  - Ensure clean mode exit, thread shutdown, and safe state transitions.

## 4. Basic locomotion helpers

- Implement `loco_move` for a specified duration.
- Use odom-mode state and non-continuous `locoClient` motion to implement `odom_move(target_dx, target_dy, target_dyaw)`.
- Learn to validate motion completion, handle cancellation/failure, and avoid conflicting locomotion commands.

## 5. SLAM operation helpers

- `start_mapping()` and `stop_mapping()`
- `relocate()`
- `add_point(point_name)` and `remove_point(...)`
- `navigate_to_point()`
- `navigate_path()` — use the SLAM API's built-in complete-path navigation, rather than navigating point by point.
- `view_map()` — return the most recently saved map visualization.

During mapping, external visualization may be required: once a map is saved on the mainboard, it may no longer be accessible for visualization.

## 6. High- and low-level arm/hand (Dex3) control

- Work with `arm_sdk` and low-command topic publishers.
- Use high-level arm actions such as `face_wave` and `clap`.
- Implement `open_hand`, `close_hand`, `teach/repeat`, and `release/engage`.
- Implement `extend_arm_forward(side, ...)` by interpolating slowly and smoothly from current arm-joint poses to a saved pose.
- Understand when to use high-level actions versus low-level joint commands.

## 7. Safety and control quality

- Apply safety limits, ramping, and smooth interpolation to all motion.
- Understand threading, synchronization, and safe shutdown.
- Detect publisher signal staleness.
- Handle publisher signal transitions safely, especially while switching controllers, modes, or command sources.

## 8. Audio, ASR, and conversational control

- Access microphone input through the ROS 2 `audio_msg` topic.
- Know that the robot must be in wake-up mode before microphone input is available. At present, wake-up mode can only be toggled through the app or remote controller.
- Integrate automatic speech recognition (ASR).
- Bonus task: build a chatbot using OpenAI API calls and microphone input.

## 9. Reference implementations to study

- `sdk_wrapper.py` — native SDK usage and DDS/environment setup.
- `../modules/scripts/ollama_ai/nav_bot.py` — correct use of the SLAM-operation and visualization stacks.
- `../hand_pose_navigation/recognition_app_v3?.py` — an example PCA depth-point-cloud pose-estimation and IK-grasping pipeline.
- `../dev/ai_control/*` — a more complex OpenAI API stack, which appears to include an OpenAI API perception pipeline.

Review these examples critically: identify their initialization order, safety assumptions, threading model, hardware dependencies, and reusable components before adopting code.

## 10. Bonus platform and deployment topics

- Set up and operate `rgbd_server_service`.
- Set up and diagnose `jetson_wifi_connection_service`.
- Understand and use the `python_cyclonedds_ros2_environment_setup_script`.
- Set up and monitor `dashboard_service`.
- Learn Jetson-specific ROS 2 Foxy deployment knowledge, including version compatibility, environment sourcing, services, hardware/network constraints, and diagnostics.

## 11. Final task: perception-based delivery

Build a delivery pipeline that combines perception, grasping, arm control, and SLAM navigation:

1. Read basic RGB-D data.
2. Use the OpenAI API perception pipeline.
3. Estimate ArUco-marker poses.
4. Estimate end-effector poses while accounting for the wrist-to-palm offset.
5. Use inverse-kinematics end-effector control.
6. Execute pickup:
   - `extend_arm_forward`
   - open the hand
   - estimate an end-effector trajectory
   - move with IK in small increments
   - at the target gripping pose, close the hand
   - interpolate to `stable_hold_pose`
7. Keep `stable_hold_pose` during SLAM-based navigation from `pickup` to `dropdown`.
8. Execute drop-off:
   - move with IK to the target ArUco pose
   - open the hand
   - interpolate to the extended-arm pose
   - release

The OpenAI API perception pipeline, IK-control helpers, and other useful helpers will be provided to participants. The academy focus is on understanding, integrating, testing, and safely operating these components.


## 12. Bonus: ROS 2 package development

- Create a small Python ROS 2 package with ros2 pkg create, package metadata, setup configuration, and a console-script entry point.
- Implement a minimal node with a publisher, subscriber, timer, parameters, and clean shutdown.
- Practice subscribing to a robot-facing topic such as low state or SLAM status without competing with the academy wrapper's control publishers.
- Publish only to a dedicated learning/demo topic. Do not create a second publisher for safety-critical robot command topics such as lowcmd unless the ownership and controller-transition plan is explicitly approved.

## 13. Bonus: RAG (Retrieval-Augmented Generation) knowledge implementation

- Understand the RAG pipeline shape: ingest documents -> chunk -> embed -> store in a vector index -> retrieve top-k matches for a query -> assemble a grounded prompt -> call the LLM.
- Build a small knowledge base from academy material (this notes.txt, todo.txt, sdk_wrapper.py docstrings, notebook markdown cells) as a first ingestion exercise.
- Chunking: split by heading/section rather than fixed character counts where possible; keep chunk size small enough to fit several retrieved chunks in context alongside the system prompt and conversation.
- Embeddings: reuse the existing OpenAI client pattern already used for the chatbot bonus task (`05_bonus_services_audio_chatbot`) and the perception pipeline in `util.py` — call the embeddings endpoint once per chunk, cache the vectors locally (e.g. a `.json`/`.npy` file) so re-runs don't re-embed unchanged content.
- Vector store options for a bonus-scale exercise: start with a flat in-memory store (list of vectors + cosine similarity) before reaching for a dedicated vector DB (Chroma, FAISS, Qdrant); a flat store is enough to demonstrate retrieval correctness on a small corpus.
- Retrieval: given a user query, embed it, rank chunks by cosine similarity, take top-k, and log which chunks were retrieved for debuggability.
- Grounding: inject retrieved chunks into the system/user prompt with clear delimiters and instruct the model to answer only from provided context, citing which chunk supported each claim.
- Integrate with the ASR/chatbot bonus flow: microphone -> ASR transcript -> RAG retrieval over academy docs -> grounded OpenAI chat completion -> Piper TTS response, so the robot can answer questions about itself/the academy material by voice.
- Evaluate: keep a small set of Q/A pairs to sanity-check retrieval quality and catch regressions when the knowledge base changes.
- Safety/scope note: this is a software/knowledge exercise — it does not touch locomotion, arm, or DDS command topics; keep it decoupled from safety-critical publishers.

## 14. Bonus: Simulation knowledge (MuJoCo, Gazebo, Isaac Lab)

Learn to validate robot behaviors in simulation before (or instead of) running on hardware — useful for iterating on locomotion, arm control, and perception logic safely.

- MuJoCo
  - Understand the MJCF model format, how the G1/Dex3 URDF/MJCF assets map to joints, actuators, and sensors.
  - Run a basic MuJoCo simulation loop (`mujoco.MjModel`, `mujoco.MjData`, `mj_step`) and drive joints with simple position/torque commands.
  - Use the built-in viewer for visual debugging; compare simulated joint trajectories against the interpolation/ramping logic used in the real `extend_arm_forward` and low-level arm helpers.
  - Note where MuJoCo is well-suited: fast, accurate contact dynamics for arm/hand manipulation and grasp-force tuning.

- Gazebo
  - Understand SDF/URDF world and model description, plugins, and the ROS 2 <-> Gazebo bridge (`ros_gz_bridge` or equivalent) for topics like odometry, IMU, and joint states.
  - Spin up a G1 (or simplified) model in a Gazebo world and confirm the same ROS 2 topics used by the real robot (e.g. odom-mode state, low state) are available in sim, so higher-level helpers can be tested without hardware.
  - Note where Gazebo is well-suited: full-robot navigation/SLAM testing, sensor simulation (LiDAR, depth camera), and multi-node ROS 2 integration testing.

- Isaac Lab (NVIDIA)
  - Understand the Isaac Lab / Isaac Sim workflow: USD-based robot/scene assets, GPU-parallel environments, and the RL-style environment API (observations, actions, rewards, resets).
  - Learn how Isaac Lab differs from MuJoCo/Gazebo: it targets large-scale parallel simulation for reinforcement learning and policy training/sim-to-real transfer, not just single-instance physics or ROS 2 integration testing.
  - Explore an existing G1 locomotion or manipulation task config if available in Isaac Lab's included environments, and understand how a trained policy would be exported and connected to the real `loco_move`/`odom_move`/arm helpers.

- Cross-cutting bonus exercise: pick one behavior implemented for the real robot (e.g. `odom_move` closed-loop arrival, or `extend_arm_forward` interpolation) and reproduce it in at least one simulator, comparing simulated vs. real joint/pose trajectories to build intuition for the sim-to-real gap.
